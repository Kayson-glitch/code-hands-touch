# 修掉点击 bug + 用「字形密度」重建明暗对比

## 1. 移除遗留的点击揭示（bug 来源）

马赛克色块层已经删掉，但点击锁定（click-lock）的整套逻辑还留着：点击后那只手会出现一块永久的「乱码圆盘」——字符被随机替换、并被强行染成高光色，且再点一次才收回。这就是你看到的 bug。

要删的部分（都在 `src/components/AsciiHandsFooter.tsx`）：

- `pointerdown` 监听与 `onDown` 处理函数，以及 cleanup 里的 `removeEventListener`
- `lockRef` 状态与每帧的 `stepLock` / `lockEase` / 半径脉冲计算
- 逐格渲染里的整段 "Click-lock reveal (per hand)" 分支
- 只被它使用的常量（`LOCK_*` 等）

结果：交互只剩 hover 的流体墨迹轨迹，点击不再产生任何视觉状态。

## 2. 为什么参考站的明暗对比那么强

调研结论（ASCII 渲染原理 + 该站做法）：

1. **对比来自字形的「墨量」，不是字符颜色。** 参考站用统一的一种深色画所有字符，明暗完全由字符本身覆盖的墨面积决定（空格→点→斜杠→实心块）。人眼在白纸上看到的是"墨点密度"的差异，非常锐利。
2. **我们现在把两套机制叠在一起互相抵消。** 当前实现既按亮度换字符，又按亮度把字符颜色从浅灰渐变到炭黑。暗部字符本来墨量就小，又被涂成浅灰 → 直接消失；亮部字符墨量大又被涂黑 → 只剩两端。中间调因此被"洗白"，看起来发灰、没有体积。
3. **字符集太长、太"平"。** 70 级 Bourke 长坡在 10px 的格子里，相邻十几个字符的实际墨量几乎无差别，等于把对比摊平。参考站只用十几个墨量差异明显的字形。
4. **他们对采样亮度做了额外的对比增强**（归一化→幂函数→反归一化），让区域边界更清楚，而不是忠实还原原图灰阶。

## 3. 据此调整手部效果

- **统一墨色**：所有字符用同一个近炭黑（约 `rgb(24,25,28)`），去掉「按亮度调字符灰度」的那套映射。明暗交给字形密度。
- **短而陡的字符坡**：把 70 级坡换成约 12–14 级、墨量阶梯清晰的坡（例如 `` ` `` `.` `:` `-` `=` `+` `*` `%` `#` `@` 一类），并保留现有的分指（partId）局部拉伸。
- **亮度对比增强**：在采样后的亮度上加一次幂函数对比增强（归一化 → `pow` → 反归一化），拉开手指与掌面的分离。
- **极暗格直接不画**：低于阈值的格子留白（纸色），让轮廓利落，而不是画一个看不见的浅灰字符。
- **保留**：流体墨迹交互（hover 时提升字形密度 + 上色）、入场生长动画、分指逻辑、抖动，全部不动。
- 只在字符层微调墨色浓淡（很小幅度）以避免死板，主对比一律由字形承担。

## 技术要点

改动集中在 `src/components/AsciiHandsFooter.tsx`：`RAMP` 常量、`brightnessToIdx` 采样段（约 450 行附近的曲线）、逐格着色段（约 1240–1280 行的 `r/g/bl` 计算），以及第 1 节列出的 click-lock 全部代码路径。染料场（`DYE_*`）逻辑保持不变，仅改为在统一墨色基础上叠加颜色。
